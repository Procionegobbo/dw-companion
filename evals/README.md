# Evals — labelling guide

## Purpose

This directory holds the eval harness for the Dungeon World assistant: three labelled
datasets (router, rules QA, move classification), configs, and the runner (`evals/run.py`)
that drives the assistant end to end against them and writes a report to `evals/reports/`.

The datasets currently committed under `evals/datasets/` are **candidates only**. They were
drafted from `data/normalized/moves.json` and `data/normalized/sections.json` — never by
running the assistant or any model configured in `evals/configs/*.toml` — and every row is
marked `"reviewed": false`. No number produced by the runner is meaningful until the project
owner has reviewed and corrected these labels. That review is a deliberate pause point
(handoff milestone 8): spec 010 (tuning) must not start, and no number from this harness may
appear in the README or `docs/decisions.md`, before it is done.

## The three dataset files

All three files live in `evals/datasets/`, one JSON object per line (JSONL), UTF-8, LF line
endings, a trailing newline, no blank lines. Ids are `router-NNN`, `rules-NNN` and
`move-NNN` (three digits from `001`, in file order).

```jsonc
// router.jsonl — does the router pick the right intent for this message?
{"id": "router-001", "message": "Can I use Defy Danger to dodge a falling rock?", "expected_intent": "action_description", "reviewed": false}

// rules_qa.jsonl — answerable rows cite the section(s) that answer the question and
// list the atomic facts a correct answer must state; unanswerable rows have both lists empty.
{"id": "rules-001", "message": "What happens when I take my Last Breath?", "expected_section_ids": ["moves/last-breath"], "key_facts": ["You roll with no stat bonus added", "On a 10+ you cheat death and remain alive"], "reviewed": false}
{"id": "rules-040", "message": "How many spell slots does a 5th-level wizard have?", "expected_section_ids": [], "key_facts": [], "reviewed": false}

// move_classification.jsonl — which move (or "no_move") does this action trigger?
{"id": "move-001", "message": "I swing my axe at the orc in front of me.", "expected_move_id": "hack-and-slash", "acceptable_alternatives": [], "reviewed": false}
```

`expected_intent` is one of `rules_question`, `action_description`, `out_of_scope`.
`expected_section_ids` and `expected_move_id`/`acceptable_alternatives` must name real
section and move ids (checked against `data/normalized/` by the loader). `acceptable_alternatives`
should only be used for genuinely ambiguous move cases — not as a hedge.

## Rule R-LABEL — labels come from the owner, never from the model under test

This rule is binding on every file under `evals/datasets/` and on every story that touches
this harness:

1. **Labels are written or validated by the project owner (an experienced GM).** They are
   never generated by the model under test. That means no model configured in any
   `evals/configs/*.toml` file, and no output of the assistant itself. Agents, including
   whoever drafts candidate rows, may draft **candidate** rows. A candidate row is untrusted
   until the owner has reviewed it.
2. **Every row has a `reviewed` field.** Only the owner sets it to `true`, after reviewing
   that row's message and labels. **No story of this spec may write `"reviewed": true` in any
   file under `evals/datasets/`.** The drafting story commits every row with
   `"reviewed": false`.
3. **The runner refuses to run on any row whose `reviewed` is not exactly JSON `true`.** That
   includes a missing key, `false`, `"true"`, `1` and `null`. The refusal covers every
   selected dataset, happens before any runtime is built or any network call is made, exits
   with code `3`, and has **no override flag**.
4. **No metric is meaningful until the owner has reviewed and labelled the rows.** Until
   then, the runner cannot produce a report on the committed datasets. That is intended:
   this harness ends with a **pause for the owner's review**. Spec 010 must not start, and no
   number may appear in the README or `docs/decisions.md`, before the owner has reviewed the
   datasets and run the first report.

## Owner review procedure

Once the three files are drafted (or whenever you want to add to or correct them), review
every row yourself, step by step:

1. For each row, check the message reads like a real table utterance.
2. Check or correct the labels against the cited rules text (`/rules/<section_id>/` on the
   site, or `data/normalized/sections.json`).
3. Add or remove `acceptable_alternatives` only for genuine ambiguity.
4. Delete rows you cannot label confidently.
5. Set `"reviewed": true` yourself, row by row; never bulk-replace without reading.
6. Commit the reviewed files in their own commit
   (`chore(evals): owner review of <dataset>`).

## Dataset Drafting coverage checklist

Whoever drafts candidate rows (or extends these files later) must satisfy this coverage.
Items marked *(test)* are enforced by `evals/tests/test_committed_datasets.py`; the rest is
a manual checklist for the drafter and the owner.

| Dataset | Coverage |
|---------|----------|
| `router.jsonl` | ≥ 40 rows *(test)*; each intent ≥ 8 rows *(test)*; ≥ 5 mixed cases (an action that also asks a rule → `action_description`); ≥ 5 adversarial cases (prompt injection, requests to ignore instructions, other games' rules, chit-chat phrased like a rules question). |
| `rules_qa.jsonl` | ≥ 40 rows *(test)*; ≥ 8 unanswerable *(test)*; answerable rows have 1–5 key facts, each a short atomic claim taken from the cited section text; questions span moves, character creation, the GM chapter, equipment and classes. |
| `move_classification.jsonl` | ≥ 80 rows *(test)*; every one of the 21 move ids is an `expected_move_id` at least once *(test)*; each of the 8 basic moves ≥ 3 rows with different phrasings *(test)*; ≥ 15 `no_move` rows *(test)*; ≥ 2 rows pairing `defy-danger` and `hack-and-slash` (one expected, the other in `acceptable_alternatives`, either way) *(test)*; ≥ 2 rows pairing `spout-lore` and `discern-realities` *(test)*. `acceptable_alternatives` only for genuinely ambiguous cases. |

## How to run

    make eval CONFIG=baseline

Equivalent to `uv run --env-file .env python -m evals.run --config baseline --dataset all`.
Override `DATASET` (`router`, `rules_qa`, `move_classification` or `all`) and `BUDGET`
(USD) as needed, for example:

    make eval CONFIG=baseline DATASET=router BUDGET=1.50

The run requires `OPENROUTER_API_KEY` and the Langfuse keys in `.env` (every eval run is
traced). While any selected dataset has an unreviewed row, the run refuses before any of
that.

## Exit codes

- `3` — rule R-LABEL: a selected dataset has at least one row whose `reviewed` is not
  exactly JSON `true`. The error names the dataset and the offending ids. There is no
  override; review and label the rows (see above) and run again.
- `4` — the budget guard. Either the pre-flight cost estimate exceeded `--budget-usd` (no
  paid call was made), or the in-flight backstop stopped the run partway through (a partial
  report is written with `status: "aborted_budget"`). Raise `--budget-usd` or `BUDGET` if the
  larger spend is intended.

Other exit codes: `0` completed; `2` a usage, config, dataset-schema, environment,
runtime-build or pricing error (see the message on stderr).

## Reports

The runner never commits a report. After a successful run, inspect
`evals/reports/<date>-<config>.json` and `.md`, and commit the ones you want to keep as
evidence — that is a deliberate owner act, not something the CLI or CI does for you.

## Tuning round

Spec 010 adds a second config (`classifier-mini`), the offline `evals/compare.py` CLI and a
`make compare` target that read two to four committed report JSON files, check that they are
comparable, and write one Markdown comparison. Those stories deliver tooling only, verified
against fixture reports: they do not run a real comparison, choose a configuration, or write
the ADR below. No eval number appears in this file, in `README.md` or in `docs/decisions.md`
because of them. The comparison, the choice and the ADR are **owner-gate steps**, below,
performed after the datasets are reviewed and both configs have been run for real.

### Owner Procedure

1. Make sure the datasets are reviewed (rule R-LABEL above) and committed, and the working
   tree is clean.
2. On one commit, on the same day: `make eval CONFIG=baseline` and
   `make eval CONFIG=classifier-mini`. Both must exit `0`.
3. `make compare REPORTS="evals/reports/<date>-baseline.json evals/reports/<date>-classifier-mini.json"`.
4. Read *Changed cases*. Spot-check a few flipped cases in Langfuse (session id = the
   report's `run_id`).
5. Apply the decision guidance below and note the outcome, or your override and its reason.
6. Commit both reports and the comparison file: `chore(evals): tuning round <date>`.
7. Append the ADR from the template below to `docs/decisions.md`, pasting the block between
   the comparison markers verbatim.
8. Set the chosen `MODEL_*` values in your local `.env`, and use them for deployment.
   `.env.example` stays empty.

### Decision guidance (spec 010 D14)

Keep the cheaper config unless the more expensive one meets all of these:

- (a) the metric its change targets improves by more than 2 cases' worth (for
  `classifier-mini`: move accuracy, more than 2 × (100/n) pp);
- (b) on the dataset of that targeted metric (for `classifier-mini`: `move_classification`),
  candidate-only flips exceed reference-only flips by at least 3;
- (c) no other headline rate regresses by more than 2 cases' worth.

These thresholds are final unless the owner changes them in writing here before running the
tuning round. The owner may also override the outcome, and the ADR must then give the reason.

### ADR template

Verbatim except the angle-bracket placeholders, which the owner fills in from the real files
(spec 001 D15 format):

```markdown
## ADR-<NNN>: Model configuration from the tuning round

Date: <YYYY-MM-DD>
Status: Accepted

### Context
Spec 007 shipped provisional model choices. The tuning round compared `<reference>` and `<candidate>` on the owner-reviewed eval datasets (<dataset>: sha256 <first 12 hex>, …) at commit <short sha>. Reports: `<json paths>`. Comparison: `<comparison path>`.

### Decision
Use `<chosen config>`: router `<id>`, classifier `<id>`, answer `<id>`, embeddings `<id>`; `GraphSettings` at defaults.

<paste the comparison table block, markers included>

Decision guidance (spec 010 D14): <met / not met, with the flip counts>. <Override reason, if any.>

### Consequences
- Replaces the provisional model values in ADR-<provider ADR number> ("Model provider: OpenRouter for chat and embeddings"); its provider decision stands.
- `MODEL_*` for local runs and deployment use the values above; `.env.example` stays empty.
- Re-run the round when a dataset changes, a model is delisted or repriced, or the graph changes.
```
